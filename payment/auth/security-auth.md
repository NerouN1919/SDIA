# AuthN, AuthZ

Для Idp был выбран Keycloak. Он работает для AuthN и AuthZ клиентов физ-лиц, мерчантов и платёжного провайдера  

## Физ лица
Когда клиент заходит на сайт, то идёт навторизированный запрос на бэкенд, который на стороне API Gateway проверяет наличие сессии в Redis.  
При наличии сесии по ней достаются access и refresh токены 
Для дальнейшей маршрутизации проставляется в заголовок запроса JWT токен, что позволяет сервисам самим выполнять AuthZ  

Если сессия в Redis не найдена, то мы редиректим пользователя на страницу логина IdP, где он заполняет данные, мы получаем AUTH_CODE, по которому в дальнейшем происходит callback API Gateway, который в свою очередь по нему достает access и refresh токен из IdP  
Полученные токены мы сохраняем в Redis по сессии и создаем редирект для сохранения сессии в куки 

## M2M
Токен валидируем на стороне API Gateway, так как он кеширует в себе публичные ключи Keycloak, а в других сервисах это будет выглядеть как нагромождение логики, что излишне. В других версивах мы выполняем только AuthZ по токену  

Для интеграции M2M внешний сервис сначала сам получает JWT токен в IdP сервисе и в дальнейшем с этим токеном идёт обращения к внутренним сервисам через API Gateway.

## Модель ролей
Роли разделяются на:
- USER
- ADMIN
- EXT_SYSTEM  

Для USER:
- /api/v1/payments
- /api/v1/wallet
- /api/v1/payments?{filters}
- /api/v1/payments/{id} - с ограничением для своих платежей

Для ADMIN
- Все как для USER, но без ограничений
- /api/v1/wallet/funds/commit
- /api/v1/wallet/funds/reserve
- /api/v1/wallet/funds/release

Для EXT_SYSTEM:
- API мерчантов

## Проброс контекста
Во все внутренние сервисы пробрасывается JWT токен(token propagation) для дальнейшей AuthZ
