# Resilience-паттерны по взаимодействиям

| Взаимодействие | Таймаут | Retries | CB | Bulkhead | Rate Limit | Fallback | Обоснование |
|---|:---:|:---:|:---:|:---:|:---:|:---:|---|
| **Orchestrator/BFF → Wallet Service** | + | | + | + | | + | Для освобождения ресурсов при зависании Wallet Service используем таймаут с фоллбэком, то есть отправляем запрос на проверку платежа, создался ли он и если да - вызываем процесс компенсации платежа. Так как Wallet Service - проходной сервис, то будет много запросов и в данном случае нужно не грузить сервис при отказе, тут используем CB. Ретрай экспоненциальный с джиттером, 3 попытки. CB должен стоять на вызове Wallet Service. При 50% неудачных запросов - переходит состояние в Half-Open, через 15 секунд пропускаем тестовые запросы|
| **Wallet Service → Transaction Service** | | | | + | | | Необходим Bulkhead на уровне Transaction Service, чтобы изолировать ресурсы и обрабатывать разные события независимо друг от друга(применяется на уровне БД и консьюмеров). |
| **Transaction Service → Payment Provider** | + | + | + | + | | + | Необходим таймаут, так как внешний провайдер для нас - «чёрная коробка». При ошибке соединения нужны ретраи. На нашей стороне при ошибке таймаута мы не знаем, что с платежом, и переводим его в статус PENDING и асинхронно дообрабатываем. Можно изолировать пул HTTP-соединений(bulkhead), тем самым не блокировать входящие запросы. CB сразу будет обрывать соединения к внешнему провайдеру, если он неактивен, тем самым избегая излишней нагрузки мёртвым сервисам. Ретрай экспоненциальный с джиттером, 3 попытки. CB должен стоять на вызове Payment Provider. При 70% неудачных запросов - переходит состояние в Half-Open, через 45 секунд пропускаем тестовые запросы|
| **Orchestrator/BFF → PaymentQueryService** | + | | + | + | | | Таймаут необходим, чтобы освобождать ресурсы Orchestrator/BFF при возможных задержках либо багах. CB сразу будет отсекать нерабочие запросы, если сервис недоступен. С помощью Bulkhead ограничиваем ресурсы для взаимодействия с разными микросервисами. CB должен стоять на вызове PaymentQueryService. При 50% неудачных запросов - переходит состояние в Half-Open, через 15 секунд пропускаем тестовые запросы|
| **Notifications Service → SMTP Server** | + | + | + | | | | SMTP-серверы бывают медленными и чтобы не держать лишний коннекшен - нужен таймаут. Ретраи необходимы, когда SMTP возвращает 4xx ошибку (просит отправить позже). С помощью CB не грузим сервис и сеть при недоступности сервиса. Ретрай экспоненциальный с джиттером, 3 попытки. CB должен стоять на вызове SMTP сервера. При 50% неудачных запросов - переходит состояние в Half-Open, через 30 секунд пропускаем тестовые запросы|
|**Transaction Service → Core Integration** | + | + | + | + | | + | Необходим таймаут, так как Core - легаси-сервис и может долго отвечать. CB сразу отбрасывает запросы, если сервис лежит. Bulkhead изолирует ресурсы к сервису от других вызовов, тем самым делая его независимым. Также необходим фоллбэк, так как проверка критическая и без неё провести платёж не можем - в статус PENDING и дообрабатываем. Ретрай экспоненциальный с джиттером, 3 попыткию. CB должен стоять на вызове Core Integration. При 50% неудачных запросов - переходит состояние в Half-Open, через 30 секунд пропускаем тестовые запросы|

Rate Limiting стоит только на API Getaway, ограничивая запросы по IP пользователей.
