# Коммуникации

## Клиент -> API Gateway
Тип - синхронная  
Протокол/стиль - HTTPS/REST  
Обоснование: Синхронная связь, так как пользователь должен сразу видеть результаты своих дейтсвий. Используется REST, так как повышается простота интеграции. Браузеры не поддерживают gRpc напрямую Очередь не используется, так как синхронная связь.  
Консистентность: синхронная консистентность(пользователь сразу видит баланс, результаты своих действий и тд)  

## API Gateway -> Auth Service
Тип - синхронная  
Протокол/стиль - HTTPS/gRpc  
Обоснование: Синхронная связь, так как требуется немедленная авторизация/аутентификация. Межсервисное взаимодействие - gRpc, т.к. быстрее работает, определенная protobuf схема, по сравнению с REST  
Консистентность: синхронная консистентность(пользователю сразу должен видеть свои права и данные личного кабинета) 

## Transaction Service -> Wallet Service
Тип - асинхронная  
Протокол/стиль - Kafka(TLS/TCP)  
Обоснование:  Асинхронная, тк на стороне wallet зарезервирована сумма транзакции и не требует моментального ответа.   
Консистентность: синхронная консистентность(баланс должен сразу изменяться при транзакции)

## Transaction Service -> Core Integration
Тип - синхронная  
Протокол/стиль - HTTPS/REST для ACL слоя. От ACL до core HTTPS/SOAP  
Обоснование: Синхронная связь, так как нужен ответ по транзации от сервиса бух учета. Core предоставляет Legacy API, поэтому нужна прослойка ACL. К ACL обращаемся по REST, так как повышается простота интеграции, за ACL стоит более медленный протокол SOAP, поэтому использование gRpc излишне.  
Консистентность: синхронная консистентность(Transaction Service должен знать результат core для продолжения транзакции)

## Transaction Service -> Antifraud/Scoring Service
Тип - асинхронная  
Протокол/стиль - Kafka(TLS/TCP)  
Обоснование: В моменте нам не требуется ответ от антифрода, значит не нужно дожидаться окончания его работы. Так как в антифрод используется ML модель, то он может долго обрабатывать запрос, что тоже исключает синхронные типы связи. Нельзя допустить, чтоб данные затерялись из-за сетевых сбоев и большая нагрузка должна разбираться последовательно  
Консистентность: eventual consistency(решение о платеже не требуется тут же, а необходимо для дальнейшего принятие решение по счету пользователя)

## Transaction Service -> Notifications Service
Тип - асинхронная  
Протокол/стиль - RabbitMQ(AMQP)  
Обоснование: Отправляем уведомления пользователю и забываем про него, так как это не должно тормозить основной процесс оформления платежа.
Консистентность: eventual consistency(уведомление пользователю - не часть основного процесса платежа, в следствии чего, можно рассматривать как внешний процесс, который может быть исполнен, когда сервис будет разгружен)

## Transaction Service -> Merchant Service
Тип - асинхронная  
Протокол/стиль - Kafka(TLS/TCP)  
Обоснование: Используется как триггер для уведомления мерчантов о платеже. Payment сервису неважен ответ для оформления платежа, что исключает синхронные протоколы.
Консистентность: eventual consistency(уведомление мерчантов - не часть основного процесса платежа, в следствии чего, можно рассматривать как внешний процесс, который может быть исполнен, когда сервис будет разгружен)

## Transaction Service -> Transaction Query Service
Тип - асинхронная  
Протокол/стиль - Kafka(TLS/TCP)  
Обоснование: допускается eventual consistency, так как помощью CQRS оптимизируются сложные поисковые запросы   
Консистентность: eventual consistency(пользователю не ккритично видеть моментально транзакции)

## Analytic Transaction Service -> Transaction Query Service
Тип - синхронная  
Протокол/стиль - HTTPS/gRpc  
Обоснование: допустим прямой вызов поисковых запросов. Асинхронный подход усложнит код и не даст выигрыша в производительности и масштабировании  
Консистентность: синхронная консистентность(данные для аналитики необходимы моментально)

## Antifraud/Scoring Service -> Wallet Service
Тип - синхронная  
Протокол/стиль - HTTPS/gRpc с mTLS проверкой  
Обоснование: Синхронная связь, так как требуется немедленная блокировка карты. Межсервисное взаимодействие - gRpc, т.к. быстрее работает, определенная protobuf схема, по сравнению с REST. mTLS требуется для проверки service to service взаимодействия, так как операция критичная и не допускает других внешних вызовов.  
Консистентность: синхронная консистентность(блокировка должна происходить сразу)
